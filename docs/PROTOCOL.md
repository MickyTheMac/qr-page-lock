# PageLock protocol v1 (PL1)

Status: prototype. Not a security audit.

## 1. Page representation (PL1-PAGE)

Defined before hashing, versioned, deterministic. For each original page:

1. **Box**: the MediaBox `[llx lly urx ury]` (normalised).
2. **Content**: every content stream fully decoded and joined with a single LF.
3. **Resources**: the whole resource graph (fonts incl. embedded font files, images, nested forms,
   colour spaces, graphics states...) serialised canonically: references resolved, dictionary keys
   sorted, every value type-tagged and length-prefixed, `/Length` ignored, stream bytes as stored.

`pageHash = SHA-256(PL1-PAGE bytes)`, upper-case hex.

### Why not a pixel hash?
The brief suggests hashing a rendered page image. We tested the idea and chose a structural hash for v1
because rendered pixels differ between browsers, operating systems and GPUs (anti-aliasing, font
rasterisation), which would make honest copies fail on other devices. The structural hash covers every
drawing instruction and every resource the page uses, is identical on every device (verified: Chromium and
Node produce the same hashes), and any change that can alter what the page shows changes the hash.
Trade-off: two files that *look* identical but are built differently get different hashes (safe direction:
reported as altered). PDF.js is still pinned and used for previews and the "QR scan test".

## 2. Sealed page layout

The original page is never modified, moved or covered. Each sealed page is exactly:

```
MediaBox = CropBox = [0 0 W H+F]        Rotate 0, no annotations, no other page data
Contents = "q 1 0 0 1 -llx F-lly cm /PLOrig Do Q\nq /PLFoot Do Q\n"
PLOrig   = form XObject: BBox = original box, Resources = original resources, content = original content
PLFoot   = form XObject: BBox [0 0 W F] (clips everything to the footer band)
           Helvetica text + 1-bit QR image (PLQR)
```

`F` is the footer band height, which identifies the footer layout:

| Layout | F | Notes |
| --- | --- | --- |
| 3 (current) | 82 pt (about 1.14 in) | Nothing drawn in the bottom 0.25 in (6.35 mm; most printers only lose the last 3 to 5 mm) or within 0.5 in of the sides. QR drawn 56 pt square without a built-in white border (same module size as layout 2; the surrounding band is white). Text in two columns: "PageLock" and "Page x of y" on the top row, document ID and short fingerprint on the second, disclaimer below. |
| 2 | 108 pt (1.5 in) | Nothing drawn in the bottom 0.5 in or within 0.5 in of the sides, so a printer's unprintable margin cannot cut off the QR code or text. "Page x of y" appears once, right-aligned just below the separator line. |
| 1 | 72 pt (1 in) | Original layout. The QR code came within ~0.05 in of the bottom edge. Still accepted by the verifier so documents sealed with it keep verifying. |

All pages in one document must use the same layout. Layout changes do not change page fingerprints, the QR payload or the manifest.

The verifier checks this structure byte-for-byte, so nothing can be drawn over the original and the footer
cannot spill onto it. The footer text is regenerated from the QR payload and compared exactly.

## 3. QR payload

QR alphanumeric mode, error correction M, ~49×49 modules:

```
PL1:<docId>:<index>:<count>:<hash>:<prev|START>:<next|END>
```

- `docId`: 120 random bits from `crypto.getRandomValues`, Crockford base32 (24 chars)
- `index` 1-based, `count` total pages, hashes are full SHA-256
- No document wording, names or file names.

All page hashes are computed **before** any QR code is created.

## 4. Manifest

Ordered manifest body (canonical JSON: sorted keys, no whitespace):
`type, protocol, pageRepresentation, hashAlgorithm, documentId, createdAt, pageCount, sourcePdfSha256, pages[{index, hash, prev, next}]`.

`manifestDigest = SHA-256(canonical JSON)`. The body is embedded in the sealed PDF (catalog `/PLManifest`)
so the verifier can recompute the digest, but the embedded copy is **not trusted on its own**.

The exported reference file (`*.pagelock-reference.json`) holds the body, the digest and the SHA-256 of the
exact sealed PDF. Keep it (or just the digest) somewhere the other party cannot change, e.g. email the
receipt to both founders. A self-contained chain can be regenerated by an attacker; the independently kept
digest is what defeats that.

## 5. Verification and results

Checks: file readable · no extra revisions · no active content · every page sealed · sealed structure intact
· content matches each fingerprint · same document ID · count and order · neighbour links START↔…↔END ·
embedded manifest binds the sequence · trusted reference (optional) · exact file bytes (with reference file)
· signatures (Phase 2, section 8).

| Result | When |
| --- | --- |
| VERIFIED | All content checks pass and every signature check passes for the required number of distinct trusted signers (section 8) |
| REFERENCE MATCH | All checks pass and the trusted reference matches. Signer identity not established |
| INTERNALLY CONSISTENT | All checks pass, no trusted reference given |
| ALTERED / INVALID | Any check fails |
| UNABLE TO VERIFY | Unsupported file, no seals, unreadable QR or any inconclusive check. Never a pass |

## 6. Rejected inputs (CREATE)

Encrypted · over 25 MB or 300 pages · JavaScript / actions / launch · form fields or signature fields ·
attachments · hidden layers (optional content) · portfolios · pages with comments, links or widgets ·
rotated pages · cropped pages · non-standard UserUnit · pages narrower than 4 in · content streams using
predictors or unknown compression · already-sealed PDFs. Rejected files get a plain-English reason.
Tip: "Print to PDF" usually produces an acceptable file.

## 7. Known limits (honest list)

- Covers what pages draw. Metadata and unreferenced objects are not in page hashes; the exact-file check
  (with the reference file) catches any byte change. The Phase 2 PAdES signature must cover the PDF bytes.
- Re-saving the sealed PDF in another editor will usually break verification. Keep the original sealed file.
- Rotated or cropped pages are rejected rather than handled.
- QR modules are ~0.4 mm. Fine for on-screen and digital checks; phone scanning of printed pages is Phase 3
  and may need a larger footer.
- A printed QR identifies the expected page; it cannot authenticate the ink around it.
- Signer identity is only as strong as the authority in the trust file (section 8).

## 8. Signing (Phase 2)

### 8.1 Signature format
- **PAdES baseline B-T**: `/SubFilter /ETSI.CAdES.detached`, CMS SignedData with `content-type`, `message-digest`
  and `signing-certificate-v2` signed attributes, plus an RFC 3161 `signature-time-stamp` unsigned attribute.
  ECDSA P-256 with SHA-256. Built with PKI.js 3.4.3 (pinned).
- Each signature is a new **incremental revision**: an invisible signature field (`/Rect [0 0 0 0]`, no appearance)
  on the last page, its `/Sig` dictionary, and the `/AcroForm` entries pointing to it. Nothing that draws is touched,
  so page fingerprints are identical before and after signing. Earlier bytes are never rewritten.
- The signed `/Reason` is the exact consent statement, naming the page count, document ID and manifest digest:
  `PageLock consent: I have reviewed all N pages of document <ID> and agree to the whole document. Document
  fingerprint (manifest digest): <digest>.` Agreement is once per document (decided 26 Nov 2026).
- Signing refuses to run without explicit consent (two ticks in the app) and refuses copies that do not verify.
- Interoperability: pyHanko 0.29 (an independent PAdES validator) reports both signatures
  `INTACT:TRUSTED, TIMESTAMP_TOKEN<INTACT:TRUSTED>` (`scripts/interop/validate_pyhanko.py`).

### 8.2 Verification
Revision 1 (up to the first `%%EOF`) is the sealed original; all Phase 1 checks run on it, and the reference file's
exact-file hash is compared with it. Then, for each later revision:

| Check | Fails when | Inconclusive when |
| --- | --- | --- |
| Only signatures were added after sealing | a revision adds or changes anything except one invisible signature field, its signature, the form list, the catalog's `/AcroForm` and the page's `/Annots` | |
| Each signature covers the whole file as signed | byte range has gaps, does not end at its revision, or bytes follow the last signature | |
| Mathematically valid | CMS signature or message digest wrong, certificate not bound | |
| Consent | statement missing or names another document | |
| Trusted authority | | certificate does not chain to the trust file at the trusted time |
| Not revoked | revoked before the timestamp | no valid CRL from the issuer |
| Trusted timestamp | token does not match the signature | missing, or authority untrusted |
| Required signers | | fewer than `requiredSigners` (default 2) distinct fully valid signers |

Outcome: any fail gives ALTERED / INVALID. VERIFIED needs every content check and every signature check to pass with
a trust file. Otherwise the result falls back to REFERENCE MATCH or INTERNALLY CONSISTENT, and the signature checks
show why. PageLock is stricter than general PDF validators: it treats any non-signature revision as tampering.

### 8.3 Trust file (`*.pagelock-trust.json`)
`signerAuthorities` and `timestampAuthorities` (PEM), `revocationLists` (PEM CRLs), `requiredSigners`,
`requireTimestamp`. The PageLock service publishes its own at `GET /api/trust`.

### 8.4 Sign-off log
See `docs/SERVICE.md`. Each founder submits a statement `{documentId, manifestDigest, pageCount, signedPdfSha256,
counterSigns, signerCertSha256, statedAt}` signed with the same key as their PDF signature. The second founder's
`counterSigns` is the first entry's hash ("double signed"). Entries form one append-only SHA-256 hash chain; the
log countersigns and timestamps each. Only the fingerprint and sign-off time are public.
